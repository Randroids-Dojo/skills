## Playable interaction

Preserve the chosen genre and input model. Describe the player's action, consequence, constraint or decision, and feedback before expanding content. Use the existing verb/GDD record; maintain the path referenced by this project's playtest instructions.

- Test one representative interaction early. Action games may need continuous control and physics; turn-based, card, text, and clicker games may use discrete input and remain still between actions.
- Fix the earliest failed dependency before adding detail or effects. Keep supporting menus, accessibility, and setup where the intended experience needs them.
- Keep presentation effects separate from authoritative state. Check release/cancel, failure/recovery, repetition, and affected accessibility modes.
- Close gameplay work with actual input, the expected state change, and readable feedback in the intended view. A compile, screenshot difference, animation, or UI count alone does not establish gameplay quality.
- Use the existing project checks and evidence records. Stop at declared acceptance; provide a concrete build for any remaining required human judgment.

Use `randroid-game-feel` for the detailed workflow when available. Its optional probes collect observations; they do not certify that a game is fun or complete.

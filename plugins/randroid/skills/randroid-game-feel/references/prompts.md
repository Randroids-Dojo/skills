# Task prompts with observable outcomes

Adapt these to the existing project contract. They are workflow examples, not claims about particular models or vendors. Do not introduce delegation, an engine migration, or new authority through a prompt template.

## First playable interaction

```text
Build one representative slice of [game], preserving [genre, stack, controls].
The player [action] using [input] to [consequence], while [constraint or decision] matters.
Show the accepted, blocked, and failed/recovered cases through [feedback].

Test the highest uncertainty first: [control / decision / moving assembly / game camera].
Include only the content, input setup, and accessibility needed to evaluate that interaction.
Done when actual input produces the expected state change and readable feedback in [scenario],
recovery works, and [required checks] pass. Attach the build and play evidence.
Stop when those conditions are met; keep any required human enjoyment review open.
```

## Existing game with a missing loop

```text
The [current behavior] does not deliver the requested [interaction].
Reproduce it in the running build and identify the earliest failed dependency.
Preserve the fiction, chosen genre, accessibility, persistence, and working systems.
Fix one coherent cause, then exercise the same input/scenario before and after.
Report observed consequences and remaining gaps. Pixel motion or widget counts do not prove the loop.
```

## One feedback problem

```text
Improve [verb/event]: currently [specific perceptible problem].
Separate acknowledgment, execution, and feedback before choosing an effect.
Keep state authoritative and make effects bounded and reversible.
Compare the same scenario before/after, including repetition and [mute / reduced motion / alternate input].
Show why the result is more readable or responsive; do not add unrelated effects or content.
```

## Verification pass

```text
Verify [claim] in [exact build] using [supported input] and [scenario].
Record input, expected state transition, observed transition, feedback, and failure/recovery.
Use the intended camera and a repeatable initial state. Include a control trial where causality is unclear.
Check [relevant boundary cases] and attach frames or a clip with state evidence.
Report untested or inconclusive claims honestly. Do not modify the game during this pass.
```

## Refinement that has stalled

```text
[Major defect] survives [comparable attempts]. Inspect the accepted build, candidate,
and evidence before making another patch. Identify whether the representation or shared interface
causes the repeated failure. Propose and execute a small experiment that can disprove that explanation.
Compare whole views and neighboring parts as well as the close-up. Carry forward only the better
candidate and update the short current-state record. Defer dependent detail until the defect is resolved.
```

In task descriptions, name a player action and its consequence. UI nouns are allowed when they describe the intended mechanic. Specify the check that would reject the work before implementation, with a bounded completion condition. Do not turn aesthetic preference into a universal rule or route ordinary art fixes into gameplay redesign.

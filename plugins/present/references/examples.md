# Worked examples

Use these examples to learn the decisions, then apply them to the user's subject. All numerical source material below is invented for illustration. Do not reuse it as evidence about a real product or organization.

## Explain a pilot without overstating it

Illustrative source: "In a pilot with 12 volunteers, the median time to draft the weekly report was 18 minutes using the current workflow and 11 minutes using the prototype. Review time was not measured. The same people tried both workflows; order was not randomized."

A supported heading is: "Pilot participants drafted reports faster with the prototype."

Show the two medians on a common scale with direct labels. Keep the sample and unmeasured review time near the claim. Say the pilot observed faster drafting under its conditions. Do not conclude that the prototype caused a general productivity increase, saved seven minutes for every report, or reduced total work. A difference between group medians is not the measured distribution of each person's savings.

For a live slide, keep the chart and decision-changing limitation readable while the presenter explains the method. For a document read alone, add the method and explain why the pilot cannot yet establish total time saved. If the user is seeking a decision, identify what additional measurement would resolve that gap without inventing a budget or commitment.

## Make a process understandable

Illustrative source: "Requests with complete data can be routed automatically. Missing or inconsistent fields require manual review. No measured time savings are available."

Show one complete request and one exception using the same visual vocabulary. Label the decision that determines the route. Show where a person must act. Prefer an annotated process or storyboard to generic capability cards.

In HTML, a case selector can switch between the complete and incomplete request while keeping the process stable. The explanation should identify which field changes the route. A static version can place the two cases together. Do not add a savings calculator until there is a defensible model and suitable inputs.

## Show when a model changes the decision

Illustrative assumptions for an operational comparison: "The existing process takes 12 minutes per case. The proposed process takes 8 minutes per case plus 120 minutes of recurring setup work each week. Assume comparable cases and an unchanged error rate for this example; neither has been measured."

For n cases per week, current effort is 12n minutes and proposed effort is 8n + 120 minutes. They are equal at 30 cases. Below 30, the proposed process takes more effort under these assumptions; above 30, it takes less. Show the assumption about error rates rather than implying it has been established.

A useful control changes weekly case volume and updates both effort values, a comparable chart, and the explanation. Verify n = 0, 20, 30, and 40 independently: the paired values are 0/120, 240/280, 360/360, and 480/440 minutes. Add a reset and a clear indication of the selected volume. Print the assumptions, threshold, and representative scenarios with their values.

The model illustrates a conditional tradeoff. It provides no evidence that a real organization achieves these timings or can ignore error-related rework.

## Replace a vague tagline with the actual relationship

Input heading: "One budget. Two apps. A choice you can examine."

If the source only establishes a comparison of allocation approaches, use "Compare shared and separate app allowances."

If the source also establishes that the shared allowance permits unused capacity to be consumed by either app, explain that behavior in the body. If priority protection depends on reservations or scheduling rules, state those conditions. Do not invent them from the heading. Keep concise labels such as "Shared allowance" and "Separate allowances" where they help a comparison.

## Prepare an agent handoff

When the user wants guidance for another agent, provide the source material, intended audience and decision, required format and constraints, proposed reading sequence, necessary evidence, and any missing inputs. Name the specific interactions worth considering and the questions they would answer. Include the verification and delivery requirements that apply.

Keep the handoff proportional to the task. Do not turn an outline request into a new deck, website, branded method, or mandatory pilot. If authoring is requested, use the handoff as working context and continue to the actual artifact.
